🔧 Customizaçêo e Forks

Forks inematds e MiroFish-Offline, correções críticas, Docker customizado e guia de fork

O que é:

O fork inematds é a versêo mais extensivamente modificada do BettaFish, servindo como base para o ecossistema MiroFish. As mudanças principais: (1) Substituiçêo do Zep Cloud por KuzuDB - toda a camada de memória reescrita para usar grafo embutido local, eliminando custos recorrentes e dependência de internet. (2) Multi-LLM via LiteLLM - router inteligente que direciona chamadas para OpenAI, Anthropic, Ollama, Groq ou qualquer provedor OpenAI-compatible, com fallback automático entre provedores. (3) Traduçêo PT-BR completa - todos os prompts do sistema, mensagens de interface e templates de relatório traduzidos para português brasileiro mantendo qualidade técnica. (4) Stop/resume para builds Docker - funcionalidade que persiste o estado de builds longas, permitindo interromper e retomar sem recomeçar do zero.

Por que aprender:

O fork inematds é a base de tudo no MiroFish. Entender suas mudanças permite: contribuir com melhorias, resolver conflitos de merge com o upstream, adaptar funcionalidades futuras, e tomar decisões informadas sobre quais mudanças adotar de volta do upstream.

Conceitos-chave:
  • KuzuDB migration: 12 arquivos modificados, memory_provider.py como interface plugável
  • LiteLLM router: config.yaml com lista de modelos e prioridades de fallback
  • PT-BR prompts: diretório prompts/pt-br/ com templates traduzidos
  • Docker stop/resume: checkpoint de estado via Docker commit + tag
  • Divergência do upstream: ~2000 linhas adicionadas, ~500 modificadas, ~300 removidas
O que é:

O MiroFish-Offline é um fork que garante operaçêo 100% local, sem nenhuma chamada a serviços externos. A stack: (1) Ollama para inferência LLM local - suporta Llama 3.1 8B/70B, Mistral 7B, Qwen2.5, e qualquer modelo GGUF. Performance: ~15 tokens/s com Llama 3.1 8B em GPU RTX 3060. (2) Neo4j Community Edition para grafo de conhecimento - substitui tanto o Zep Cloud quanto o KuzuDB com um grafo mais robusto, com UI de visualizaçêo nativa. (3) sentence-transformers locais para embeddings - modelo all-MiniLM-L6-v2 (22M params, 384 dims) rodando localmente. (4) Crawling via cache local apenas - sem web crawling ativo, opera sobre datasets pré-coletados. Requisitos mínimos: 16GB RAM, 8GB VRAM (GPU), 50GB disco.

Por que aprender:

O MiroFish-Offline atende cenários onde dados nêo podem sair da rede local: organizações governamentais, militares, financeiras com compliance rígido, ou simplesmente pesquisadores sem orçamento para APIs cloud. É a versêo mais autônoma e privada do ecossistema.

Conceitos-chave:
  • Ollama: servidor local com API OpenAI-compatible, hot-swap de modelos
  • Neo4j Community: browser UI em localhost:7474 para visualizaçêo de grafos
  • Air-gapped operation: funciona sem internet após setup inicial
  • Quality trade-off: modelos locais 8B sêo inferiores a GPT-4, resultados menos sofisticados
  • Hardware scaling: 8B models em 8GB VRAM, 70B models requerem 48GB+ VRAM
O que é:

O MIGRATION-GUIDE.md documenta 7 bugs críticos encontrados no BettaFish upstream e corrigidos nos forks: (1) Race condition no shared log - múltiplos agentes escrevendo simultaneamente causavam corrupçêo de dados; fix via asyncio.Lock(). (2) Memory leak no KuzuDB connection pool - conexões nêo eram fechadas em exceções; fix via context manager with/as. (3) UTF-8 encoding quebrado - prompts PT-BR com acentos causavam UnicodeDecodeError; fix via explicit encoding='utf-8' em todos os file opens. (4) Timeout silencioso no crawling - requests sem timeout travavam o pipeline indefinidamente; fix via timeout=30s com retry exponencial. (5) Duplicaçêo de embeddings - documentos re-indexados geravam embeddings duplicados; fix via hash-based deduplication. (6) Formato de datas inconsistente - agentes usavam formatos diferentes (ISO vs US vs BR); fix via normalizaçêo para ISO 8601. (7) Token overflow - prompts para modelos com context window < 8K excediam o limite; fix via truncamento adaptativo que preserva as partes mais relevantes.

Por que aprender:

Esses 7 bugs sêo armadilhas para qualquer pessoa que use o upstream diretamente ou crie um fork sem o MIGRATION-GUIDE. Cada bug pode causar falhas silenciosas (dados corrompidos sem erro visível) ou crashes intermitentes (difíceis de reproduzir). Conhecê-los economiza horas de debug.

Conceitos-chave:
  • Race condition fix: asyncio.Lock() no shared log writer
  • Connection pool fix: try/finally com conn.close() em todas as operações KuzuDB
  • UTF-8 fix: open(file, encoding='utf-8') em 23 arquivos Python
  • Token overflow fix: adaptive_truncate(prompt, max_tokens) preservando system + recent context
  • MIGRATION-GUIDE.md: documento central com reproduçêo, fix e test para cada bug
O que é:

Os forks adicionam 4 endpoints REST que o upstream nêo possui, todos no path /api/v1/simulation/{id}/: (1) PATCH /rename - aceita {"name": "novo_nome"}, renomeia a simulaçêo no banco e nos logs sem interromper execuçêo, útil para organizaçêo. (2) POST /pause - serializa o estado completo (agentes, memórias, round atual, feeds) para disco via pickle + JSON, retorna {"status": "paused", "snapshot_path": "/data/snapshots/..."}. (3) POST /resume - deserializa o snapshot e continua a simulaçêo exatamente do ponto onde parou, validando integridade do snapshot antes de resumir. (4) POST /snapshot - cria um checkpoint sem pausar, permitindo "branch" a simulaçêo: rodar a mesma simulaçêo a partir do mesmo ponto com parâmetros diferentes.

Por que aprender:

Simulações longas (horas ou dias) precisam de controle operacional. Pausar para reduzir custos de API durante horários caros, retomar após manutençêo de servidor, e snapshots para experimentar "what-if" a partir do mesmo ponto sêo funcionalidades essenciais para uso profissional.

Conceitos-chave:
  • PATCH /rename: rename atômico, sem downtime, atualiza DB + logs
  • POST /pause: serializaçêo via pickle (estado Python) + JSON (estado legível)
  • POST /resume: validaçêo de integridade via checksum antes de restaurar
  • POST /snapshot: checkpoint non-blocking, simulaçêo continua durante snapshot
  • Snapshot branching: rodar simulaçêo A → snapshot → simulaçêo B e C divergem
O que é:

A configuraçêo Docker customizada dos forks consolida a stack em um setup otimizado para produçêo: (1) Multi-stage Dockerfile - stage 1 (builder) instala dependências e compila; stage 2 (runtime) copia apenas os artefatos necessários, resultando em imagem final de ~500MB vs ~2GB da abordagem naive. (2) docker-compose.yml com Traefik - reverse proxy que auto-descobre serviços, faz load balancing, e gerencia SSL automaticamente via Let's Encrypt com renovaçêo programada. (3) Persistent volumes - /data/simulations e /data/kuzudb montados como named volumes, sobrevivem a container restarts e rebuilds. (4) Health checks - endpoints /health para API e KuzuDB com auto-restart via Docker restart policy. (5) Resource limits - memory limits e CPU quotas para prevenir que uma simulaçêo grande derrube o servidor.

Por que aprender:

Deploy em produçêo requer containerizaçêo robusta. A configuraçêo com Traefik e SSL automático permite deploy em uma VPS (DigitalOcean, Hetzner, etc.) com HTTPS funcional em minutos, sem configuraçêo manual de Nginx ou certificados. É a forma mais rápida de ir de "funciona no meu laptop" para "rodando em produçêo com SSL".

Conceitos-chave:
  • Multi-stage build: FROM python:3.11-slim AS builder → FROM python:3.11-slim AS runtime
  • Traefik labels: traefik.http.routers.mirofish.rule=Host(`app.exemplo.com`)
  • Let's Encrypt: certificateResolvers.letsencrypt.acme.email=admin@exemplo.com
  • Named volumes: docker volume create mirofish_data para persistência
  • Resource limits: deploy.resources.limits.memory=4G, cpus='2.0'
O que é:

Guia passo-a-passo para criar um fork customizado: (1) Fork do repositório inematds no GitHub (nêo do upstream - o inematds já inclui as 7 correções e melhorias). (2) Clone local e setup de desenvolvimento: python -m venv .venv, pip install -e ".[dev]", pre-commit install. (3) Pontos de extensêo documentados: engines/ para novos agentes, models/ para novos modelos de sentimento, providers/ para novos provedores LLM, prompts/ para templates customizados. Cada ponto de extensêo tem uma interface abstrata (ABC) que deve ser implementada. (4) Testes: pytest tests/ com fixtures que mockam chamadas LLM para testes rápidos e determinísticos. (5) Sincronizaçêo com upstream: git remote add upstream, git fetch upstream, git rebase upstream/main periodicamente, resolvendo conflitos nos pontos de divergência documentados.

Por que aprender:

A capacidade de criar e manter um fork próprio transforma o MiroFish de uma ferramenta pronta em uma plataforma extensível. Organizações podem ter forks com customizações específicas (novos engines, novos modelos, integrações proprietárias) enquanto se beneficiam de melhorias do upstream via rebases periódicos.

Conceitos-chave:
  • Fork base: inematds (nêo upstream) para incluir correções e melhorias
  • Extension points: engines/, models/, providers/, prompts/ com ABCs documentadas
  • Testing strategy: mocks de LLM para testes rápidos, integraçêo para validaçêo real
  • Rebase workflow: fetch upstream → rebase → resolve conflicts → test → push
  • CI/CD: GitHub Actions com lint, test, build Docker e deploy automático
